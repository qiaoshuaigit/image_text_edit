## 二、核心数据流

```
用户上传文件
    ↓
load_image()
    - PIL 读取原图（关闭 MAX_IMAGE_PIXELS 限制）
    - 转 OpenCV BGR 格式
    - 缩放到 2000px 用于显示
    - 存到 _state['orig_bgr']（原图）和 _state['display_bgr']（显示图）
    ↓
用户点击"开始识别"
    ↓
do_detect()
    - 用 OCRDetector 检测文字区域
    - 每个文字区域存为 {text, x_min, y_min, x_max, y_max, w, h}
    - 生成 DataFrame 表格数据
    - 画 OCR 框到预览图上
    ↓
用户在表格里编辑操作（替换/移除/字号等）
    ↓
用户点击"生成结果"
    ↓
do_generate() 【核心函数，优化过的批量渲染】
    ├─ 第一步：遍历表格，收集所有需要处理的行
    │   - 操作="不改" → 跳过
    │   - 操作="移除" → 只擦除，不写新文字
    │   - 操作="替换" → 擦除 + 写新文字
    │   - 把要擦除的区域画到 mask 上
    ├─ 第二步：ROI 局部擦除
    │   - 只在 mask 边界框内做 Inpaint（不是整张图）
    │   - 大图片性能优化点
    ├─ 第三步：批量渲染所有文字
    │   - 一次性 BGR→RGB→PIL 转换（不是每行转一次）
    │   - 在同一个 PIL Image 上画所有文字
    │   - 一次性 PIL→RGB→BGR 转回
    │   - 大图片性能优化点
    └─ 缩放显示尺寸返回给界面
```

## 四、关键设计决策

### 4.1 为什么关闭 PIL 的 MAX_IMAGE_PIXELS？

PIL 默认有"解压炸弹"保护，超过 1.78 亿像素的图片会报错。医学大图经常 7.9 亿像素，所以必须关闭：
```python
Image.MAX_IMAGE_PIXELS = None
```

### 4.2 为什么用 gr.File 不用 gr.Image 上传？

Gradio 的 Image 组件在处理超大数组时会崩溃（把图片转成 numpy 数组再传给后端，内存占用太大）。改用 File 上传，后端用 PIL 读取原图，再缩放显示。

### 4.3 为什么渲染要批量做？

旧版本：每一行文字都做一次完整的 BGR→RGB→PIL→BGR 转换。
- N 行文字 = N 次全图格式转换
- 每次转换都是几亿像素的大数组拷贝
- 200M 图片生成一次要 20-30 秒

优化后：
- 一次性 BGR→RGB→PIL 转换
- 在同一个 PIL Image 上画所有文字
- 一次性 PIL→RGB→BGR 转回
- 生成时间降到 5-8 秒

### 4.4 为什么擦除要做 ROI 局部？

旧版本：整张图做 Inpaint，即使 mask 只有文字那一小块。
优化后：只在 mask 的边界框内做 Inpaint，大图片上快很多。

### 4.5 颜色空间为什么容易出 bug？

- OpenCV 用 BGR 顺序
- PIL 用 RGB 顺序
- Gradio Image 组件用 RGB 顺序

之前出过 bug：把 Gradio 的 RGB 颜色直接传给 OpenCV 当 BGR 用，导致导出图片颜色错乱。现在所有颜色转换都显式做，不能猜。

```python
_state = {
```

**注意**：Gradio 的状态是每次请求隔离的，这里用全局变量是因为单用户本地工具，多用户场景需要改成 Gradio State。

## 七、性能优化历史

| 优化点 | 优化前 | 优化后 |
|---|---|---|
| 渲染方式 | 逐行全图转换 | 批量一次转换 |
| 擦除方式 | 整张图 Inpaint | ROI 局部 Inpaint |
| OCR 检测 | 全尺寸检测 | 先缩放再检测 |
| 图片上传 | gr.Image（崩溃） | gr.File + PIL 读取 |
| PIL 解压炸弹 | 默认限制（报错） | 关闭限制 |
